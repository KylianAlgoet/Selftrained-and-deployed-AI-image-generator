| R1 | 8 GB VRAM insufficient for chosen base model/training config | medium | high | **Training now measured 2026-08-04 (Prototype 3), so this risk is quantified on both sides.** *Inference* (M3/M4): SD 1.5 needs 2675 MiB @512 and 3892 MiB @512×1536; IP-Adapter adds a fixed ~1249 MiB at both geometries; a rank-8 LoRA adds **+3.04 MiB and does not scale with geometry**. *Training* (M5): rank-8 UNet-attention LoRA at tier 0 peaks at **3133 MiB @512×512** and **5183 MiB @512×1536**, both with no tier escalation — native deck-format training fits with 1738 MiB spare. **Mechanism measured, not assumed:** post-load allocation is identical at both geometries (2066.56 MiB) and the optimizer-step peak barely moves (2108.93 → 2118.76), while the forward/backward peak rises 3114 → 5183. **Activations dominate, optimizer state does not**, so gradient checkpointing (tier 1) is the correct first escalation and a lower-memory optimizer would be the wrong move. The kohya fallback (DR-004) is not needed. Residual risk sits in R12, not here: it is the *combined* stack, not training alone, that is tight | mitigating (inference and training both measured; combined-stack margin tracked in R12) |

| R12 | **Combined SD 1.5 + LoRA + IP-Adapter does not fit 8 GB at 512×1536** | **medium** | **high** | **ACCEPTANCE ITEM DISCHARGED 2026-08-04 (EXP-019). The stack FITS — by 202 MiB.** The mandatory smoke test ran in the fixed order (512×512 first, deck format only after it passed), each arm in a fresh process, with both adapters confirmed live simultaneously by reading the UNet back (128 LoRA modules + 16 IP-Adapter attention processors). Measured at 512×1536: **5143.73 MiB allocated, 7985.5 MiB device used of 8187.5 physical — 202.0 MiB spare, i.e. 2.5 % of the device.** **This is not comfortable headroom and must never be described as such.** It is *less* margin than IP-Adapter alone had in EXP-013 (222 MiB), because the LoRA takes 20 MiB of device memory on top. No overflow flag fired and no tier escalated — the same pattern that made SDXL look viable in EXP-004 until its figures were read against the ceiling, which is why the number is always quoted against the ceiling. Geometry was never reduced to make it pass. **RE-SCOPED, NOT CLOSED:** the risk is no longer "does this stack fit" but "**does anything added to it still fit**". Prototype 5 must treat 512×1536 + LoRA + IP-Adapter as the **memory ceiling of the production path**: a second adapter, a higher LoRA rank, a larger reference batch, or ControlNet for layout control all have 202 MiB to fit into. Escalation path if a future addition breaks it: inference tiers 1–4 in separate runs; documented last-resort fallback remains img2img at zero extra VRAM, accepting its near-copy behaviour (R13) | mitigating (tested stack fits; margin is 2.5 % and any addition is at risk) |
| R13 | **Reference conditioning reproduces the reference image (near-copy / originality failure)** | medium | high | **Occurred and quantified 2026-08-01 (EXP-013, EXP-014).** All 6 copy-risk flags in M4 (dHash ≤ 6) are **img2img at 512×1536**, three at **dHash 0–1**, i.e. perceptually indistinguishable from the reference; Kylian scored them `originality 1` / `copy_or_overfitting_risk 1`. Median dHash for img2img at medium is 27 @512×512 but **5 @512×1536**. Mechanism: img2img forces the reference into the output resolution, so when the aspect already matches nothing is cropped and denoising starts from an essentially intact copy. **Mitigation: IP-Adapter selected as the primary method (DR-008) — it produced no near-copy flag at any scale or geometry.** img2img is retained only as a labelled fallback. Keep the dHash ≤ 6 flag and the copy-risk sheet in every future evaluation; flagged outputs are surfaced, never deleted. Prototype 5 must not expose an img2img mode at the deck format without this warning | occurred (mitigated by method selection) |
