# Prototype 0 — Static interactive 3D skateboard viewer

**Milestone:** M1 (issue #2) · **Dates:** planned 2026-07-28→30, executed 2026-07-27 (ahead of schedule) · **Status:** implemented; see results below.

## Research question and hypothesis (RQ9)

> How can decal artwork be correctly mapped onto a 3D skateboard deck — UV layout, nose–tail orientation, and dynamic texture updates — in a browser viewer?

**Hypothesis:** a procedurally generated, UV-mapped deck mesh in React Three Fiber can display a decal texture with correct nose–tail orientation and swap it at runtime without reload, with orientation controlled purely by the UV layout (no texture pre-rotation).

## Alternatives and decision

Four approaches were compared with weighted criteria (implementation time, texture/UV control, testability, licensing, React integration, performance, deadline risk) in the approved milestone plan. **Chosen: procedural deck geometry inside R3F** (score 131/140), over an external glTF model (86), plain Three.js (112), and `<model-viewer>` (77). Rationale and fallbacks: `docs/decisions/DR-005-deck-geometry-source.md`.

## Scope delivered

- `apps/web` — Vite 6.4.3 + React 19.2.8 + TypeScript 5.8 scaffold (Vite pinned to 6.x because the audited Node 20.18.0 does not meet Vite 7's ≥20.19 requirement).
- `apps/web/src/deck/deckGeometry.ts` — pure, deterministic popsicle-deck `BufferGeometry`: concave, **asymmetric kicks (nose 0.17 > tail 0.12)** so orientation is physically meaningful, documented UV convention (decal face: u across width, **v=1 at nose**, v=0 at tail), material groups (0 = decal underside, 1 = top/rim).
- `apps/web/src/viewer/DeckViewer.tsx` — R3F scene, lights, orbit + zoom (drei OrbitControls), reset via controls handle; `preserveDrawingBuffer` enabled (needed for canvas export — also required by the MVP's download feature).
- `apps/web/src/viewer/ViewerControls.tsx` — DOM-only control bar (decal buttons, reset, labelled inverted-UV demonstration toggle), kept Canvas-free for jsdom testability.
- Two **self-created SVG test decals** (`apps/web/public/decals/`): an orientation-test design (NOSE text + arrow, TAIL, green LEFT/blue RIGHT edge stripes) and a distinct geometric design. Licence: project-original assets, authored in-repo (comment headers in each SVG). **No external assets were downloaded anywhere in this prototype.**

## Asset licensing

All 3D geometry is generated by project code; both decals are hand-authored SVGs committed with licence headers. Nothing to verify externally; risk R10 (external model licensing) avoided entirely.

## Tests (real output)

`npm run test` (Vitest 4.1.10): **13 tests, 2 files, all passing** — UV range invariants, v=1→nose mapping, demonstration-flag inversion, bounding box, downward winding of the decal face, determinism, nose>tail kick asymmetry; ViewerControls selection/reset/toggle behaviour and decal-registry sanity. `npm run lint` clean; `npm run build` succeeds (bundle 1.11 MB minified / 309 KB gzip — three.js dominates; acceptable for the prototype, code-splitting deferred).

Boundary: jsdom provides no WebGL, so actual rendering is validated manually in Chrome (below), not in unit tests.

## Orientation result (the honest finding)

**The first real render was already correct**: with the documented UV convention (v=1 at nose) plus Three.js' default `flipY = true`, the decal image top landed at the nose, text readable and unmirrored when viewing the deck underside. **No real orientation defect occurred, so no fix commit exists.** The "incorrect mapping" evidence is a **controlled demonstration**: a clearly-labelled dev toggle (`invertV`) renders the decal with inverted V so the jury can see what the defect would look like (TAIL upside-down at the physical nose end). It is banner-labelled in the UI and named accordingly in the evidence files — it is not a record of a real failed attempt.

## Real problems encountered (documented, not hidden)

1. **jsdom 27 incompatible with Node 20.18.0** — its CSS chain `require()`s an ES module (needs Node ≥20.19); pinned `jsdom@26.1.0` and defaulted Vitest to the `node` environment with per-file jsdom opt-in. (Risk R5 materialized in mild form.)
2. **Stale canvas captures** — `requestAnimationFrame` pauses in background tabs, so canvas exports repeated old frames (detected by identical file hashes). Fixed with a dev-only `EvidenceCaptureHook` exposing a synchronous render trigger; also useful for M8 E2E screenshots.
3. **Chrome blocks repeated automatic downloads** — evidence export switched from `<a download>` clicks to POSTing the canvas data-URL to a temporary local save-server (session tooling, not project code).

## Experiment registry note

No `EXP-###` row is created for this prototype: it contains no generative-model experiment. The registry starts with Prototype 1's benchmarks, per `docs/05-experiment-methodology.md`.

## Conclusion

Hypothesis **confirmed**: UV layout alone controls decal orientation on a procedural deck in R3F; textures swap at runtime without reload; camera controls and reset behave. DR-003 (React+Vite+TS+R3F) is validated by working software — the fallback to plain Three.js was not needed.

## Impact on next iterations

- The MVP (M7) can consume generated PNGs exactly as these SVG textures are consumed (same pipeline); `preserveDrawingBuffer` already supports the planned download feature.
- The decal aspect ratio used here (512×2000 ≈ 1:3.9) becomes the reference input for the aspect-ratio experiments in Prototype 1 (RQ8).
- Deck geometry constants (`DECK_LENGTH`, `DECK_WIDTH`, …) are the single source of truth for later texture-size decisions.
